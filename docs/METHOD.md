# 可信度工程：三个块，一个方法

> 这份文档不讲"我做了什么功能"，只讲**这三个块共用的判断框架**。
> 代码分别在 `codegen/`（trace / 生成闭环）和 `house_data_RAG/2_scripts/evaluate/`（检索评测）。

---

## 0. 一句话

> **三个块看起来是三件事（执行 trace、生成校验、检索评测），
> 但都在回答同一个问题：『怎么证明 AI 真的做了它说的事』。**

| 块 | 验证什么 | 在哪 |
|---|---|---|
| **trace** | **工具说改了**，真的改了吗 | `codegen/trace.py` |
| **生成闭环** | **模型说生成了**，真的合法吗 | `codegen/planner.py` |
| **检索评测** | **系统说检索到了**，真的是那个吗 | `house_data_RAG/docs/EVAL.md` |

---

## 1. 问题：AI 的"假成功"

普通系统只有两种结局：**成功 / 失败**。
但 AI 系统里真实存在第三、第四种：

| 结局 | 例子 | 普通日志能发现吗 |
|---|---|---|
| 成功 | 命令生效了 | ✅ |
| **明确失败** | 报错、超时 | ✅ |
| ★★★ **假成功** | **说成功了，但回读对不上** | ❌ **不能** |
| ★★ **说不出答案** | 模型明确表示"我不知道" | ❌ 常被判成"失败" |

★★★ **"假成功"是这套方法的核心目标** —— 因为它**不报错、不崩溃，只是结果是错的**。

★ 我在两个项目里都撞到了它：

| 项目 | 假成功长什么样 |
|---|---|
| Civ6 审计 | Java 少声明 `players` 字段 → 前端 3 项检查拿到 `undefined` 静默跳过 → **界面 30%、README 34%** |
| RAG 评测 | **Precision@5 = 100%**，但 top5 里 53% 是**没有面积的记录** |

## 2. 三个块各自的做法

### ① trace：把「结果」拆成「执行 + 回读」

```python
trace["ok"]             = executor(**args)        # 工具说得怎么样
trace["readback_value"] = reader(result, **args)  # 真实状态是什么
trace["outcome"]        = classify(trace, expected)
```

**五类结局**（不是两类）：

```
SUCCESS / MISSING_INFO / SILENT_FAILURE / EXPLICIT_FAILURE / UNKNOWN
```

★ **关键**：`readback` 必须是真的重新读一次 —— **不是"工具返回的 success 字段"**。

★ 同一个框架**同时用在两个场景**（换个 executor / reader 就行）：

| 场景 | 执行 | 回读 |
|---|---|---|
| 工具调用 | 下发命令 | 重新读取真实状态 |
| 模型生成 | 调模型拿输出 | 用校验函数确认合法 |

### ② 生成闭环：把「缺信息」和「答错」分开

```
VALID        → 直接用
INVALID      → 重试（把错误回喂，模型能改）
MISSING_INFO → ★ 不重试，返回"需要用户澄清"
```

★★ **这是最重要的一个判断**：
> **重试的语义是"你答错了，改一改"。**
> **而"缺信息"的语义是"你没给我足够的信息，我该问你"。**
> **混在一起，模型就会陷入「编造 → 被拒 → 再编造」的死循环。**

★ 改造前后（5 条任务）：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 一次通过率 | 0% | **100%** |
| 平均重试 | 2.8 次 | **1.0 次** |
| ★ **编造次数** | **1 次** | **0 次** |

### ③ 检索评测：分层测，而不是只报一个总分

```
filter 解析层：100%        ← parse_query 对不对
检索层（标准）：1.00        ← Precision@5
★ 检索层（质量）：53% 垃圾   ← 自己加的指标
```

★ **为什么必须加第三个**：**Precision 只检查"符不符合条件"，不检查"是不是真房源"**。

## 3. ★★★★ 三个块共用的四类手段

| # | 手段 | 具体做法 |
|---|---|---|
| **1** | **指标可复算** | 每个对外数字都能指到"产出它的脚本"，不手写进文档 |
| **2** | **缺陷公开** | README 里列未修的缺陷（不是"已修"清单） |
| **3** | **执行可 trace** | 每次调用记参数/耗时/回读，结局分五类 |
| **4** | **失败可定位** | 错误信息**写给下游看**（给人看的报错、给模型看的错误回喂、给人看的 trace） |

★★ **第 1 条是我吃过亏之后定的**：
> 两个项目都出现过"文档数字漂移"（102 回合写成 130、14 个依赖写成 12）。
> 所以现在规矩是：**指标必须由脚本产出，改完要回读核对**。

## 4. ★★★★★ 三个块里出现了「同一个错误」三次

这是**把三个块放一起看才发现的**：

| 层 | 同一个错误 |
|---|---|
| 校验层 | `None` 被判成"类型错" → 三态 |
| 逻辑层 | `MISSING_INFO` 被判成"失败" → 触发重试 → 不重试 |
| trace 层 | `MISSING_INFO` 被判成"假成功" → 五类结局 |

> ### **同一个分类错误，会在每一层重复出现 ——**
> ### **因为每一层都在用「二值判断」表达一个「三值现实」。**

★★★ **这不是粗心，是"表达方式不够"** —— 布尔装不下三态，所以每一层都漏一次。

★★ **所以真正的修法不是"下次注意"，而是**：**把枚举引进来**（五类结局 / 三态校验）。

## 5. 这套方法的边界（比它能做什么更重要）

| # | 做不到 | 为什么 |
|---|---|---|
| **1** | **"用户意图"层拦不住** | "用户有没有要求期限"这件事，校验看不见 —— 只能靠 prompt 或人抽检 |
| **2** | **标准指标有盲区** | Precision 高不代表结果可用（53% 垃圾率的例子） |
| **3** | **正确答案是大集合时 Recall@K 失效** | "天河区 500 万以下"有 878 条答案，top5 最多进 5 条 |
| **4** | **样本小** | 评测只有 5 条查询，只能说明"这一层不是坏的"，不能量化"多好" |
| **5** | **"回读"本身也会错** | 如果回读函数写错了，会得出假的"假成功" |

★★★ **第 1、2 条是这次最值钱的认知**：
> **校验只能拦"你能用规则描述的错"。**
> **而"标准指标全绿"也不等于"质量没问题"。**

---

## 6. 如果重来

1. **先定义"结局分类"，再写代码** —— 我三次都在"二值/三值"上翻车
2. **每个写操作从第一天就配一个读操作** —— 否则永远发现不了假成功
3. **评测先跑一小步**（5 条就够）—— 它会先暴露上游问题，比补全指标更有价值
4. **别用"留空"当兜底** —— `if x: 赋值` 这种写法静默吞掉 71% 的数据，比裸 `except` 还隐蔽
